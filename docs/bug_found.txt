DEF-1  Write endpoints have no authentication / authorization
-----------------------------------------------------------------------------------
Components affected : A (Centres/Routes), B (Vehicles), C (Trips, Drivers), D (Passengers, Bookings, Fares, Payments, Support)
Severity / Priority : High / P1  (security: unauthenticated data modification, money, personal data)
Status              : FIXED - retest PASSED

Description
  CentresController, RoutesController, VehiclesController, TripsController,
  PassengersController and most of BookingsController had no [Authorize] attribute.
  Any anonymous caller (no login at all), or a logged-in Commuter, could change data
  that only staff should be able to change. Only MaintenanceRecords, Drivers, Incidents,
  Payments, AgentRecovery and the /me endpoints were protected.

  Impact observed in the tests (all returned a success status on the unfixed code):
    - Anonymous user created a centre and a bay                (201 Created)
    - Anonymous user closed a centre                           (204 No Content)
    - Commuter archived a route                                (204 No Content)
    - Anonymous user created a vehicle and deactivated one     (201 / 204)
    - Commuter updated a vehicle                               (204 No Content)
    - Anonymous user created a trip and changed its status     (201 / 204)
    - Commuter cancelled a trip                                (204 No Content)
    - Anonymous user listed ALL passengers incl. phone numbers (200 OK, personal data leak)
    - Commuter read another passenger's profile and wallet     (200 OK)
    - Anonymous user topped up ANY wallet by any amount        (201 Created, financial risk)
    - Anonymous user created a booking that debits another passenger's wallet (201 Created)
    - Anonymous user cancelled a booking (reached the handler: 404 instead of 401)
  Found in a second pass (audit of every controller for write endpoints without [Authorize]):
    - Anonymous user created, changed or deactivated a FARE RULE (e.g. set a fare to 0.01)
    - Anonymous user triggered a STRIPE REFUND for any booking      (POST /payments/bookings/{id}/refund)
    - Anonymous user started a checkout on behalf of any passenger  (POST /payments/checkout)
    - Anonymous user listed and created support requests            (passenger names, trips, descriptions)
    - Anonymous user listed all drivers with phone and licence numbers (GET /drivers, GET /drivers/{id})

Steps to reproduce (unfixed code)
  1. Start the API with no Authorization header / cookie.
  2. POST /api/v1/centres with {"code":"HAX","name":"Hack","city":"X","district":"Y"}
  3. Observe 201 Created (expected 401 Unauthorized).
  4. POST /api/v1/passengers/{id}/wallet/top-ups with {"amount":100000}
  5. Observe 201 Created and the wallet balance increased (expected 401).
  Automated: dotnet test apps/api.Tests/api.Tests.csproj --filter "FullyQualifiedName~AccessControl"

DEF-2  Updating a route or a route direction fails (HTTP 500)
-----------------------------------------------------------------------------------
Component affected  : A (Centres and Network - routes and ordered stops)
Severity / Priority : Medium / P2  (the "Update route stops" operation of the feature is broken)
Status              : FIXED - retest PASSED

Description
  PUT /api/v1/routes/{routeId} and PUT /api/v1/routes/directions/{directionId} replace the
  stop list. The code removed the old stops and then assigned a brand-new list to the
  navigation property (route.Stops = ToStops(...)). The new RouteStop objects already carry
  a client-generated Guid id, so Entity Framework treats them as existing rows to UPDATE
  instead of new rows to INSERT. The save then fails with:

    DbUpdateConcurrencyException: The database operation was expected to affect 1 row(s),
    but actually affected 0 row(s)

  and the API returns HTTP 500. The route-level update also created the stops with
  RouteId = Guid.Empty.

Steps to reproduce (unfixed code)
  1. Create a route with 3 stops: POST /api/v1/routes (stops: Stop 0, Stop 1, Stop 2).
  2. Update it: PUT /api/v1/routes/{id} with a new name and 2 different stops.
  3. Observe HTTP 500 (expected 204 No Content) and the stops are not replaced.
  4. Same result for a direction: PUT /api/v1/routes/directions/{directionId} with new stops.
  Automated: dotnet test apps/api.Tests/api.Tests.csproj --filter "FullyQualifiedName~RouteCrudTests"

Failing tests (2) - see backend-before-fix.log
  Centres/RouteCrudTests.Update_ChangesRoute_AndReplacesStops
  Centres/RouteCrudTests.UpdateDirection_ReplacesStops_AndKeepsThemOrdered

Fix applied (apps/api/Controllers/RoutesController.cs)
  Route update : db.RouteStops.RemoveRange(old stops) then
                 db.RouteStops.AddRange(ToStops(request.Stops, routeId: route.Id))
                 so the new stops are explicitly INSERTed with the correct RouteId.
  Direction update : same pattern, run inside a transaction with the delete saved before the
                 insert, so the unique index on (RouteDirectionId, SequenceOrder) is not violated.

Retest result
  Both tests pass; the stops come back in the new order with the new names.
  Full suite: 233 passed, 0 failed (backend-after-fix.log).

DEF-3  Parallel bookings oversell a trip (capacity ignored)
-----------------------------------------------------------------------------------
Component affected  : D (Passengers and Fares - booking, seat allocation)
Severity / Priority : High / P1  (more passengers sold than the vehicle can carry)
Status              : FIXED - retest PASSED

Description
  POST /api/v1/bookings checks the remaining capacity (OccupiedCapacity + requested seats <=
  vehicle capacity) and then inserts the booking, but the check and the insert are not
  protected against other requests running at the same moment. Several requests can read the
  same "free seats" value, all pass the check, and all insert a booking. The only database
  guard is a unique index on the random boarding reference, which never collides.

Steps to reproduce (unfixed code, PostgreSQL)
  1. Create a trip whose vehicle has capacity 2 and 10 passengers with enough wallet balance.
  2. Send 10 POST /api/v1/bookings requests (1 passenger each) at the same time.
  3. Observe that more than 2 succeed. Test run result: capacity 2, 5 seats sold (5 x 201).
  Automated: Database/BookingConcurrencyTests.ParallelBookings_NeverExceedVehicleCapacity

Fix applied (apps/api/Controllers/BookingsController.cs, Create)
  The booking now runs in a transaction that first locks the trip row (SELECT ... FOR UPDATE)
  and then re-reads the occupied capacity, so concurrent bookings for the same trip are
  checked one after another. No schema change or migration was needed.

Retest result
  The test passes, 5 runs in a row, and sells at most 2 seats.

DEF-4  Parallel bookings spend the same wallet balance twice
-----------------------------------------------------------------------------------
Component affected  : D (Passengers and Fares - wallet payment)
Severity / Priority : High / P1  (financial: tickets obtained without paying)
Status              : FIXED - retest PASSED

Description
  The wallet balance is read, compared with the fare, reduced in memory and saved, with no
  lock and no concurrency token. Parallel requests all read the same balance, all pass the
  "sufficient balance" check, and each writes "balance - fare", so the later writes overwrite
  the earlier ones (lost update).

Steps to reproduce (unfixed code, PostgreSQL)
  1. Give one passenger a wallet balance of 100 and a trip with a fare of 100.
  2. Send 8 POST /api/v1/bookings requests for that passenger at the same time.
  3. Observe that all 8 bookings are created while the balance only drops from 100 to 0.00:
     8 tickets (800) were obtained for 100.
  Automated: Database/BookingConcurrencyTests.ParallelBookings_ByOneWallet_CannotSpendMoreThanTheBalance
  Related: Database/TransactionTests.TwoContexts_UpdatingTheSameRow_BothSucceed_LastWriteWins
           documents that wallets have no concurrency protection at database level.

Fix applied (BookingsController.cs, Create)
  The wallet row is locked (SELECT ... FOR UPDATE) inside the same transaction and reloaded
  before the balance check, so only one booking at a time can spend from a wallet.

Retest result
  The test passes (5 runs in a row): at most 1 booking succeeds and the balance is never negative.

DEF-5  Parallel cancellations refund one booking several times
-----------------------------------------------------------------------------------
Component affected  : D (Passengers and Fares - cancellation and refund)
Severity / Priority : High / P1  (financial: duplicate refund records, wrong ledger)
Status              : FIXED - retest PASSED

Description
  DELETE /api/v1/bookings/{id} checks that the booking is not already cancelled and later
  refunds the wallet, without locking. If the request is sent twice at once (double click,
  client retry, slow network), every request passes the "only active bookings" check and each
  one adds a Refund transaction.

Steps to reproduce (unfixed code, PostgreSQL)
  1. Create a booking that cost 100 (wallet 100 -> 0).
  2. Send 8 DELETE /api/v1/bookings/{id} requests at the same time.
  3. Observe 7 Refund transaction rows for one booking (balance shows 100 only because the
     updates overwrite each other, so the ledger and the balance disagree).
  Automated: Database/BookingConcurrencyTests.ParallelCancellations_RefundTheBookingOnlyOnce

Fix applied (BookingsController.cs, Cancel)
  The booking and wallet rows are locked inside the refund transaction and reloaded; the
  "already cancelled" check is repeated after the lock, so only the first request refunds.

Retest result
  Exactly 1 Refund transaction and a final balance of 100 (5 runs in a row).

DEF-6  Trip time without a timezone crashes on PostgreSQL (HTTP 500)
-----------------------------------------------------------------------------------
Component affected  : C (Scheduling and Dispatch) - affects every date field in the API
Severity / Priority : Medium / P2
Status              : FIXED - retest PASSED

Description
  Trip and maintenance times are stored in "timestamp with time zone" columns. Npgsql only
  accepts UTC values for these columns. A client that sends a time without "Z" or an offset
  (for example "2030-06-01T08:00:00") produces a DateTime of kind Unspecified, and saving it
  throws "Cannot write DateTime with Kind=Unspecified to PostgreSQL type 'timestamp with time
  zone', only UTC is supported", which the API returns as HTTP 500. SQLite accepts any kind, so
  the API suite could not see this.

Steps to reproduce (unfixed code, PostgreSQL)
  1. POST /api/v1/trips with "scheduledTime": "2030-06-01T08:00:00" (valid IDs for the rest).
  2. Observe HTTP 500 (expected 201 Created).
  Automated: Database/BookingConcurrencyTests.Trip_WithLocalTimeWithoutTimezone_IsStoredAsUtcInstant

Fix applied (apps/api/Data/AppDbContext.cs)
  A value converter on every DateTime / DateTime? property normalizes values to UTC before
  they are saved: local times are converted, times without a kind are treated as UTC. No
  column type changed, so no migration is needed (the migration-drift test confirms this).
  Assumption to confirm with the team: a time sent without an offset is interpreted as UTC.

Retest result
  The trip is created (201). Full suite: 293 passed, 0 failed.

DEF-7  Malformed refresh cookie returns HTTP 500
-----------------------------------------------------------------------------------
Component affected  : Shared foundation (authentication)
Severity / Priority : Low / P3
Status              : FIXED - retest PASSED

Description
  POST /api/v1/auth/refresh catches SecurityTokenException only. A cookie that is not a JWT (for example random text)
  makes the token handler throw SecurityTokenMalformedException, which is an ArgumentException, so the request ends
  in an unhandled exception and HTTP 500 instead of 401. Anyone can trigger it by sending a made-up cookie.
Steps to reproduce (unfixed code)
  1. POST /api/v1/auth/refresh with the header "Cookie: upts_refresh_token=not-a-token".
  2. Observe HTTP 500 (IDX12741: JWT must have three segments); expected 401.
  Automated: Auth/AuthenticationTests.Refresh_WithoutOrWithGarbageCookie_ReturnsUnauthorized
Fix applied (AuthController.Refresh): the catch now handles SecurityTokenException and ArgumentException.
Retest result: returns 401; test passes (def7-before-fix.log failed, def7-after-fix.log passed).

DEF-8  Stripe webhook without a signature header returns HTTP 500
-----------------------------------------------------------------------------------
Component affected  : D (Payments)
Severity / Priority : Low / P3
Status              : FIXED - retest PASSED

Description
  POST /api/v1/payments/stripe/webhook passed the Stripe-Signature header straight into Stripe's verifier. With no

  1. POST /api/v1/payments/stripe/webhook with any JSON body and no Stripe-Signature header.
  2. Observe HTTP 500 / NullReferenceException; expected 400.
  Automated: Bookings/StripeWebhookTests.MissingSignatureHeader_OrStaleTimestamp_IsRejected
Fix applied (PaymentsController.StripeWebhook): a missing or blank header returns 400 before verification.
Retest result: returns 400; all 15 webhook tests pass (def8-before-fix.log / def8-after-fix.log).

-----------------------------------------------------------------------------------
Component affected  : D (Passengers and Fares - card payment, the path the mobile app uses)
Severity / Priority : High / P1
Status              : FIXED - retest PASSED

DEF-10 Parallel refund requests ask Stripe to refund repeatedly
-----------------------------------------------------------------------------------
Component affected  : D (Passengers and Fares - refunds)
Severity / Priority : High / P1  (money: duplicate refund requests and duplicate refund records)
Status              : FIXED - retest PASSED

Description
  BookingPaymentService.RequestRefundAsync loads the booking, checks it is active and then calls Stripe. Parallel
  requests (double click, retry) all pass the check before any of them cancels the booking, so each one calls
  Stripe and records a refund. The existing guard "A refund is already being processed" never ran because the
  Refunds collection was not loaded. The same happens through DELETE /bookings/{id} for a paid booking.
Steps to reproduce (unfixed code, PostgreSQL)
  1. A confirmed booking with a successful Stripe payment.
  2. Send 6 refund requests (POST /payments/bookings/{id}/refund) at the same time.
  3. "Stripe was asked 6 times and 6 refund rows exist; expected exactly one."
  The cancel-booking route showed the same: expected 1 gateway call, actual 6 (def10b-before-fix.log).
  Automated: Database/PaymentConcurrencyTests.ParallelRefundRequests_ReachStripeOnlyOnce and
             ParallelCancellations_OfAPaidBooking_ThroughTheBookingApi_ReachStripeOnlyOnce
Fix applied (BookingPaymentService.RequestRefundAsync): the booking row is locked inside a transaction, the booking
  is read again after the lock (so a booking cancelled by the first request is seen as cancelled), and the Refunds
  collection is now loaded so the in-progress guard works. A shared helper (api/Data/DbContextLockExtensions.cs)
  provides the lock for all of these fixes.
Retest result: exactly one gateway call and one refund row; stable over 3 runs.

DEF-11 Timetable ending near midnight loops forever
-----------------------------------------------------------------------------------
Component affected  : A (Centres and Network - timetables / trip generation)
Severity / Priority : High / P1  (a request that never finishes and keeps a server thread busy)
Status              : FIXED - retest PASSED

Description
  POST /api/v1/routes/schedules/{id}/generate-trips stepped through departures with TimeOnly.AddMinutes, which wraps
  around at midnight. For a timetable whose last departure is within one headway of midnight (for example 22:30 to
  23:30 every 30 minutes), 23:30 + 30 minutes becomes 00:00, which still compares as "before 23:30", so the loop never
  ends. Any schedule ending after 23:30 with a 30 minute headway is affected.
Steps to reproduce (unfixed code)
  1. Create a schedule 22:30 - 23:30, headway 30, Everyday, and call generate-trips for any date.
  2. The request does not return (the test run was killed after 120 s although the client gave up after 15 s).
  Evidence: docs/testing/evidence/def11-before-fix.txt (isolated demonstration + the hang).
  Automated: Centres/RouteScheduleTests.Departures_* (pure-function tests, so a regression fails fast)
Fix applied: new api/Services/ScheduleTimes.cs counts plain minutes and stops at the last departure;
  RoutesController.GenerateTrips uses it.
Retest result: "22:30,23:00,23:30" and 5 other timetable shapes pass; the generator tests pass.

DEF-12 A manager can change another centre's data
-----------------------------------------------------------------------------------
Components affected : A (centres, bays, routes, timetables), B (vehicles), C (trips), D (fares)
Severity / Priority : High / P1  (broken object-level authorization: data of every centre can be changed by any manager)
Status              : FIXED - retest PASSED

Description
  After DEF-1, the write endpoints required a staff role but not the right centre. Drivers, incidents and
  maintenance records checked the centre_id claim; centres, bays, routes, schedules, vehicles, trips and fare rules
  did not. A CentreManager, Dispatcher or FleetOfficer of centre A could therefore rename or close centre B, archive
  its routes, deactivate its vehicles, cancel its trips or set its fares to 0.01.
Steps to reproduce (unfixed code)
  1. Log in as a CentreManager assigned to centre A.
  2. PUT /api/v1/centres/{centre B id}, DELETE /api/v1/routes/{B route}, DELETE /api/v1/vehicles/{B vehicle},
     DELETE /api/v1/trips/{B trip}, PUT /api/v1/fare-rules/{B fare}.
  3. All succeed (204) instead of 403.
  Automated: Auth/CentreIsolationTests (7 of 10 failed on the old code, def12-before-fix.log)
Fix applied: new api/Services/CentreAccess.cs (User.CanManageCentre: Admin, or centre_id claim equals the centre)
  applied to the write endpoints of Centres, Routes (incl. directions, schedules, generate-trips), Vehicles, Trips
  and FareRules. Moving a vehicle or trip to another centre needs rights on both centres.
Retest result: all 10 isolation tests pass; managers can still manage their own centre and Admin can manage any.
Behaviour change to confirm with the team: staff accounts with NO centre assignment can no longer change
  centre data (the same rule that already applied to drivers, incidents and maintenance).

DEF-14 Cancelling a trip does not cancel or refund its bookings

Component affected  : C (Scheduling and dispatch - trip cancellation), D (Passengers and Fares - bookings, wallet) affected
Severity / Priority : High / P1  (financial: the passenger keeps a "Cancelled" ticket but loses the fare)
Status              : FIXED - retest PASSED
Found by            : Integration/PassengerJourneyTests.CancelledTrip_RefundsThePassengersWalletAutomatically

Description
  DELETE /api/v1/trips/{id} (and PATCH .../status to Cancelled) only changed the trip status. Bookings stayed
  Confirmed, wallets were not refunded and there is no commuter cancel endpoint, so only staff cancelling each
  booking by hand returned the money.
Steps to reproduce (unfixed code)
  1. Create centre, route, vehicle, driver, trip and fare (150). Commuter registers, wallet topped up to 500, books: wallet 350.
  2. Dispatcher cancels the trip with a reason.
  3. Expected: booking Cancelled, wallet 500 with a Refund transaction. Actual: booking stays Confirmed, wallet 350.
Cause
  TripsController.Cancel / UpdateStatus never touched Bookings or Wallets. A second gap was found by the new
  parallel test: BookingsController.Create checked that the trip was open BEFORE taking the trip row lock, so a
  booking made while the trip was being cancelled could still be created and stay unrefunded.
Fix applied
  New Services/BookingCancellationService: cancelling a trip, in one transaction under a row lock on the trip, cancels every
  active booking and refunds it with the same rules as staff cancellation (wallet refund plus a Refund transaction;
  card bookings go through the existing Stripe refund path after the commit, and a failed card refund leaves that
  booking Confirmed for staff to retry). If a wallet booking cannot be refunded the whole cancellation rolls back.
  BookingsController.Cancel now uses the same service. BookingsController.Create re-reads the trip after taking the lock.
Retest result
  Journey tests 3/3 pass (def14-before-fix.log had 1 failure: wallet 350 instead of 500). New regression tests:
  Dispatch/TripCancellationRefundTests (6) and, on PostgreSQL, Database/PaymentConcurrencyTests
  ParallelTripAndBookingCancellations_RefundThePassengerOnlyOnce and BookingWhileTheTripIsBeingCancelled_NeverLeavesAPaidBookingOnACancelledTrip
  (the second failed once: 8 active bookings on a cancelled trip, wallets 3200 instead of 4000, until the re-check was added).
  Full suite: 513 passed, 0 failed.
  Not done: passengers are still not notified of the cancellation.

TOOLING AND CONFIGURATION FINDINGS (from the non-functional runs)
-----------------------------------------------------------------------------------
Not counted in the 6 defects above because they are tooling / configuration issues, not
product behaviour. Evidence is in docs/testing/evidence/.

T-1  k6 script ignored load settings (Low) - FIXED
     perf/k6/read-apis.js read __ENV.K6_VUS and __ENV.K6_DURATION. These names are reserved k6
     options, so setting them made k6 discard the scenarios and fail with
     "function 'default' not found in exports" (exit code 104). Renamed to PERF_VUS / PERF_DURATION
     and documented in the file header. Retest: a 100-VU run completed (k6-stress-100vu.log).

T-2  Web dependencies with known vulnerabilities (Medium) - OPEN
     pnpm audit on apps/web reports 37 advisories: 1 critical, 13 high, 18 moderate, 5 low
     (security-pnpm-audit.txt / .json). 34 of the 37 are reachable only through the "shadcn" package
     (including the critical one, proxy-addr, and the undici / fast-uri / js-yaml / brace-expansion /
     braces / hono / ip-address / MCP SDK findings). shadcn is a code-generation CLI, yet it is listed
     under "dependencies" in apps/web/package.json, which is why "pnpm audit --prod" reports the same
     37. 2 findings are dompurify (<= 3.4.15, patched in >= 3.4.16) reached through jspdf and
     @thunderid/react, which DO run in the browser. 1 is source-map-js, reached through the
     @tailwindcss/vite build tool.
     Suggested action: move shadcn to devDependencies, then update or override dompurify, and
     re-run the audit.

T-3  Vulnerable transitive package in the test project only (Low) - OPEN
     dotnet list package --vulnerable: apps/api has none; apps/api.Tests has
     SQLitePCLRaw.lib.e_sqlite3 2.1.6 (High, GHSA-2m69-gcr7-jv3q), pulled in by the SQLite test
     provider. It is not part of the deployed API.

T-4  Development secrets in an ignored file (Low) - OPEN
     apps/api/appsettings.Development.json holds Stripe test keys and a JWT signing key. The file is
     now git-ignored and untracked, but earlier commits that touched it (for example 2f2a7c3) may
     still contain those values in history. Suggested action: rotate the Stripe test keys and the
     JWT key, and use user-secrets or environment variables.

T-5  Bootstrap admin has a well-known default password (Medium) - OPEN
     Program.cs creates admin@upts.lk with the password "admin123" when the configuration keys
     BootstrapAdmin:Email / BootstrapAdmin:Password are not set (used in the throwaway test
     environment). If a deployment forgets to set them, the Super Admin account is guessable.
     Suggested action: fail startup in non-development environments when the keys are missing.

OTHER OBSERVATIONS (not defects, recorded for the report)
-----------------------------------------------------------------------------------
  - Each trip/booking/centre/vehicle "delete" is a soft delete (status change) and the tests
    confirm the record and its history are retained, as the component breakdown requires.
  - Business rules verified working with no defects: duplicate code/plate/phone conflicts,
    input range validation, trip conflict detection (vehicle, driver, bay window, maintenance
    day), trip status state machine, wallet debit/refund, capacity limits, refund only once.
  - The API suite runs on in-memory SQLite; the database suite (apps/api.Tests/Database, 60 tests)
    runs on real PostgreSQL 17 through Testcontainers and needs Docker. It verified with no
    defects: all migrations apply to an empty database, the model matches the migration
    snapshot (no pending migration), migrations can be rolled back to zero and re-applied,
    every unique/foreign-key/not-null/length/precision constraint, the restrict/cascade/set-null
    delete rules, the partial unique index on active booking seats, and commit/rollback behaviour.
  - Design note: FareRule has a unique index on RouteId, so a route has exactly one fare rule (the API
    even answers "Edit the existing fare instead"). This looks intentional; it means fare history
    cannot be kept by adding new rules. Confirm with the team if history is ever required.
  - Row locks now protect booking create and cancel (wallet path), card checkout, refunds and wallet top-ups.
    Not covered by a parallel-request test: the Stripe webhook handlers (they are idempotent through the stored
    event id, but that was only tested with sequential replays) and the recovery-workflow approval actions.
